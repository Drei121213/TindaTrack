## Files and code

- `ProductImportFile` reads the four-column UTF-8 CSV. Its `Row` record holds a
  name, `BigDecimal` price, integer stock and optional `LocalDate`. Missing stock
  is rejected rather than defaulted to zero. An explicit `NULL` date represents
  no expiration; an empty date is rejected to expose incomplete input.
- `ProductImportTool` is a separate command-line maintenance entry point.
  `validate` is offline, `plan` reads MySQL, and `apply` inserts a reviewed batch.
  It reuses `DatabaseConnection` and the existing ignored credential file.
- The existing `Product` model and `ProductDao` are unchanged. There is no separate
  inventory service in this project. `ProductDao.addProduct()` opens an individual
  connection per product, so calling it repeatedly would not provide a transaction
  covering the whole import. The maintenance tool uses one connection instead.
- `ProductImportFileTest` checks parsing and validation using fictional data.

The existing table is `products(product_id, name, price, stock_qty,
expiration_date)`. IDs are generated by MySQL. Names must fit `VARCHAR(150)`;
prices use `DECIMAL(10,2)` and must also satisfy the application's positive-price
rule; stocks must fit a nonnegative signed `INT`. No schema changes are needed.

The CSV header must be exactly:

```csv
name,price,stock_qty,expiration_date
```

Use decimal PHP amounts without a peso symbol, commas or exponent notation.
Use YYYY-MM-DD or literal `NULL` for expiration. Quote names containing commas
and double any embedded quotation marks. Multiline names are unsupported.
Do not resave through a spreadsheet program that changes dates or rounding.

## How the prepared transaction works

The plan records the CSV fingerprint, target server identity, and current matching
products. Apply acquires the same MySQL product-name lock used by the app, requires
an InnoDB products table, and begins a SERIALIZABLE transaction. It checks the
reviewed plan again with locking reads before inserting anything. A stale plan
causes an abort. Prepared statements bind prices with `setBigDecimal`, stock with
`setInt`, and expiration as SQL DATE or SQL NULL.

Each new row is read back by its generated ID and compared against the approved
values before commit. A private receipt records only the newly generated IDs and
their full values, along with the reviewed plan and backup fingerprint. It is
flushed before the single commit. Matching products are skipped; no UPDATE,
DELETE, schema modification or seed-data import is performed.

The tool prevents duplicate input names ignoring case and checks names using the
database's collation. If two otherwise distinct CSV names collide under MySQL
collation, it aborts the entire transaction. Rerunning the same list requires a
fresh reviewed plan and a new receipt; previously imported names should be SKIP.
The schema has no unique name constraint, so other software must honor the same
locking convention; keep other writers closed during this operation.

## Rollback and uncertain outcomes

- **Failure before commit:** the tool rolls back the whole batch. It reports
  success only after commit. A successful rollback leaves existing data unchanged;
  auto-increment IDs may have gaps. Keep any failure receipt for diagnosis.
- **Lost connection during commit or failed rollback:** do not assume the batch
  was undone and do not retry immediately. Check receipt state and query the
  recorded generated IDs on the recorded server. `PRECOMMIT` alone is not proof
  of either success or failure. Resolve the outcome before further action.
- **Commit succeeds but receipt finalization fails:** the tool reports the commit
  as successful with an incomplete receipt status. Inspect its recorded IDs; do
  not repeat an apply command to repair a file.
- **Undo requested after a confirmed commit:** SQL ROLLBACK cannot undo it later.
  Obtain separate approval for removing only the receipt's newly inserted IDs.
  Start one transaction, acquire the product-name lock, select each ID FOR UPDATE,
  and compare its name, price, stock and nullable expiration with the receipt.
  Stop and roll back if any ID is missing, changed, or referenced by other data.
  Delete only confirmed, unchanged imported IDs with prepared statements and
  snapshot predicates; check each affected-row count before committing. Never
  delete by a name range, reset the products table, or delete pre-existing matches.
  This preparation adds no automatic delete or undo command. Retain the full
  backup as a recovery option requiring its own reviewed restore procedure.

## Packaging and another computer

New installations must start with their own empty schema and local connection
settings. Build/package application code and runtime dependencies only. Exclude
this folder, credentials, backups, test databases and reports containing store
data. Never register `plan` or `apply` in the application startup or installer.

For transferring inventory intentionally, use a separate private UTF-8 export
containing these same four columns. Transfer it securely outside the installer,
review it on the destination, back up that destination database, create a target-
specific plan and import it with this manual process. Let MySQL generate new IDs;
do not copy development credentials, users or customer credit data with inventory.
Container units must be understood by the receiving store because the schema has
no separate unit-of-measure field. Keep the export private and remove transferred
copies when no longer needed.
